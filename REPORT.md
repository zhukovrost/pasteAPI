# Отчет по лабораторной 3

## Что требовалось

- Ревьюер в GitHub Actions на `pull_request` (`opened`, `synchronize`).
- Модель получает только diff PR, без остального репозитория.
- Из diff убираются lock-файлы, `dist/`, `generated/`, бинарники.
- Для большого PR ревью пропускается с понятным комментарием.
- Ответ модели — JSON с файлом, строкой и фрагментом кода.
- Чек-лист хранится в markdown-файле и передаётся модели.
- Результат публикуется комментарием в PR.
- Ошибки модели не роняют workflow.
- Ключ хранится только в GitHub Secrets, прав у токена минимум.
- Отдельно: PR с заложенными проблемами и приманками, список проблем,
  precision / recall / false positives.

## Этап 1. Чек-лист

Файл `.github/review-instructions.md` сокращён:

- **5 пунктов уровня error**: инъекции; IDOR; секреты в коде и логах;
  небезопасная работа с файлами (`../` и TOCTOU); слабая криптография.
- **2 пункта уровня warning**: проигнорированная ошибка; HTTP-клиент без
  таймаута или проверки статуса.
- Уровень `info` и правила про стиль, тесты и валидацию убраны.

В формате ответа теперь обязательны `file`, `line` и `code`. Это нужно, чтобы
бот показывал не только «где-то проблема», но и конкретное место в коде.

## Этап 2. Бот

Модуль `tools/review-bot`. Работает по шагам:

1. Читает diff, делит на файлы, убирает lock-файлы, `dist/`, `generated/`
   и бинарники.
2. Считает строки и файлы, проверяет порог 1500/40.
3. Ограничивает размер: 30 KB на файл, 120 KB на промпт.
4. Собирает system prompt с чек-листом и user prompt только с diff.
5. Просит у Gemini JSON по схеме: `file`, `line`, `code`, `severity`,
   `message`, `reason`.
6. Проверяет ответ: убирает обёртку ```json, приводит severity к
   `error`/`warning`, выбрасывает комментарии без строки или кода, комментарии
   к файлам вне diff, `info` и дубликаты.
7. Рендерит markdown: заголовок `файл:строка`, блок с кодом, проблема, причина.

Если ключа нет, модель вернула ошибку или битый JSON — бот пишет
fallback-комментарий, workflow остаётся зелёным. Обрыв ответа по лимиту токенов
обработан отдельно.

## Этап 3. Локальная проверка

`go test ./...`, `go vet ./...`, `go build` в `tools/review-bot`. Тесты не ходят
в сеть: вместо модели используется заглушка. Проверяются разбор diff, фильтры,
порог, сборка промпта, валидация ответа, fallback, вывод `file:line` и кода,
отбрасывание комментариев без строки и с `severity: info`.

## Этап 4. Workflow

1. Checkout head-коммита PR.
2. Three-dot diff: `git diff origin/<base>...HEAD`.
3. Исключения lock-файлов, `*.sum`, `dist/`, `generated/`.
4. Сборка бота, запуск, публикация комментария через `actions/github-script`.

`GEMINI_API_KEY` — из Secrets, только через `env`. `GEMINI_MODEL` — переменная
репозитория. Права: `contents: read`, `pull-requests: write`.

## Метрики

- **precision** — доля настоящих проблем среди комментариев бота.
- **recall** — доля найденных проблем среди всех заложенных.
- **FP** — комментарии, которых нет в списке заложенных проблем.

| Метрика | Значение |
|---|---|
| Найдено верно (TP) | 10 |
| Ложных (FP) | 0 |
| Пропущено (FN) | 1 |
| precision | 10 / 10 = **100 %** |
| recall | 10 / 11 = **90.9 %** |

По severity: ошибки — 6 из 7 (85.7 %), warning — 4 из 4 (100 %).
Ни одна из шести приманок не была отмечена.

Если считать md5 и сравнение `==` одной проблемой «слабая криптография», то
получается 9 верных, 1 лишний комментарий и 1 пропуск: precision 90 %,
recall 90 %.

## Что бот заметил

Бот нашёл все проблемы, которые видны в отдельной строке или в двух соседних:
склейку SQL, ключ в коде, токен в логе, path traversal, md5, сравнение через
`==`, оба случая игнорирования `json.Decode`, оба HTTP-клиента без таймаута.
Все 10 комментариев содержат файл, строку и фрагмент кода.

## Что бот пропустил

- **TOCTOU (5).** В том же файле он нашёл path traversal, но не связал
  `os.Stat` и `os.Remove` в удалении вложения.

Эта проблема требует смотреть на связь нескольких мест, а не на одну строку.

## Вывод

Пайплайн работает: diff фильтруется, порог и лимиты соблюдаются, ключ не
утекает, при сбоях модели workflow остаётся зелёным, комментарий с файлом,
строкой и кодом появляется в PR.

На этом наборе бот не выдумал ни одной проблемы (precision 100 %) и нашёл
10 из 11 заложенных (recall 90.9 %). Пропущен только TOCTOU — случай, где нужно
анализировать последовательность действий, а не одну строку.
