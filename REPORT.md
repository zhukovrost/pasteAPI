# Отчет по лабораторной 3

## Что требовалось

- ✅ Ревьюер в GitHub Actions, запуск на `pull_request` (`opened`, `synchronize`).
- ✅ Модель получает только diff PR, без остального репозитория.
- ✅ Из diff убираются lock-файлы, `dist/`, `generated/`, бинарники.
- ✅ Если PR слишком большой — ревью пропускается с понятным комментарием.
- ✅ Ответ модели — JSON `{"comments":[{"file","severity","message","reason"}]}`.
- ✅ Чек-лист хранится в markdown-файле и реально передаётся модели.
- ✅ Результат публикуется комментарием в PR.
- ✅ Ошибки модели (битый JSON, таймаут) не должны ронять workflow.
- ✅ Ключ хранится только в GitHub Secrets, прав у токена минимум.
- ✅ Отдельно: PR с заранее заложенными проблемами и приманками, список проблем,
  расчёт precision / recall / false positives.

## Этап 1. Инструкция для ревьюера

Файл `.github/review-instructions.md`. В нём 18 пунктов: security (инъекции,
IDOR, секреты, логи, слабая криптография, path traversal, CORS), correctness
(игнор ошибок, HTTP-клиент, приведение типов, TOCTOU, nil, context, даты), API и
тесты, стиль. Отдельно — что не надо писать, и формат JSON.

Зачем: один и тот же список использовался и в промпте, и при закладке проблем,
и при оценке результата.

## Этап 2. Workflow

Файл `.github/workflows/ai-review.yml`:

1. Checkout head-коммита PR.
2. Diff через `git diff origin/<base>...HEAD` — только изменения PR.
3. Исключения lock-файлов, `*.sum`, `dist/`, `generated/`.
4. Сборка бота, запуск, публикация комментария через `actions/github-script`.

`GEMINI_API_KEY` берётся из Secrets и передаётся только через `env`, в лог не
печатается. `GEMINI_MODEL` — repository variable. Права: `contents: read`,
`pull-requests: write`. Если изменено больше 1500 строк или 40 файлов, модель не
вызывается.

## Этап 3. Бот

Отдельный модуль `tools/review-bot` (SDK Gemini требует Go 1.24, приложение на
1.22). Что делает:

1. Читает diff, делит на файлы, убирает ненужные, считает строки.
2. Проверяет порог 1500/40.
3. Ограничивает размер: 30 KB на файл, 120 KB на промпт.
4. Собирает system prompt (роль + чек-лист) и user prompt (только diff).
5. Вызывает Gemini со схемой ответа, просит только JSON.
6. Проверяет ответ: убирает обёртку ```json, нормализует severity, выбрасывает
   пустые комментарии, комментарии к файлам вне diff и дубликаты.
7. Рендерит markdown для PR.

Если ключа нет, модель вернула ошибку или битый JSON — бот пишет
fallback-комментарий и завершается успешно, workflow остаётся зелёным.
Отдельно обработан обрыв ответа по лимиту токенов (`MAX_TOKENS`).

## Этап 4. Локальная проверка

`go test ./...`, `go vet ./...`, `go build` в `tools/review-bot`. Тесты не ходят
в сеть: используется фейковый клиент модели. Проверяются парсинг diff, фильтры,
порог, сборка промпта, валидация ответа и fallback. Настоящий вызов Gemini
возможен только из Actions — локально ключ не работает.

## Метрики

- **precision** — доля настоящих проблем среди комментариев бота.
- **recall** — доля найденных проблем среди всех заложенных.
- **FP** — комментарии, которых нет в списке заложенных проблем.

| Метрика | Значение |
|---|---|
| Найдено верно (TP) | 7 |
| Ложных (FP) | 1 |
| Пропущено (FN) | 7 |
| precision | 7 / 8 = **87.5 %** |
| recall | 7 / 14 = **50.0 %** |

По группам: security — 5 из 6, correctness — 2 из 5, API/тесты — 0 из 2,
стиль — 0 из 1. Ошибки уровня `error`: 5 из 7.

## Что бот заметил

Проблемы, которые видно прямо в изменённых строках: склейка SQL, ключ в коде,
токен в логе, md5, path traversal, приведение типа, `http.Get` без таймаута.
Здесь бот ошибается редко.

## Что бот пропустил

- **IDOR**: в маршруте есть проверка авторизации, но сервис не проверяет, чья
  это паста. Бот посчитал, что авторизации достаточно.
- **TOCTOU**: `os.Stat` и `os.Remove` — два отдельных действия, между ними файл
  может измениться. Бот не связал эти строки.
- **`http.DefaultClient`** в модерации. При этом `http.Get` в том же файле он
  заметил.
- **Игнор `json.Decode`**: `_ =` выглядит намеренным, последствия бот не увидел.
- **Нет валидации входа** у новых endpoint'ов.
- **Нет тестов** у 8 маршрутов. Чтобы это заметить, нужно сопоставить 14
  маршрутов и 9 тестовых функций — бот такого не делает.
- **Дублирование** валидаторов.

Ложное замечание — бот принял безопасный `fmt.Sprintf` с
whitelist-колонкой за инъекцию и поставил severity `error`.

## Вывод

Пайплайн работает: diff фильтруется, порог и лимиты соблюдаются, ключ не
утекает, при сбоях модели workflow остаётся зелёным, комментарий появляется в
PR. Бот хорошо находит простые проблемы в отдельных строках (precision 87.5 %),
но пропускает половину заложенных проблем (recall 50 %), особенно те, где нужно
смотреть на связь нескольких файлов или на отсутствие чего-то (тесты,
валидация).
